# 028 가지(브랜치) 역할 · 고객 화면 데이터 경로 · 안전 반영 구조 · 롤백안 v01후보 (2026-11-03)

025 지시 2항 이후(누락분)와 027 지시 4항에 대한 답. **읽기 검증 결과 + 준비한 도구**이며, 기본 가지 변경·자동 병합·배포는 대표 승인 전 실행하지 않았다.

## 1. 지금 실제 역할 (2026-11-03 저장소 확인)
| 가지 | 역할(실제) | 자동 작업 | 앱이 읽나 |
|---|---|---|---|
| `daejeon-setup` | **저장소 기본 가지**. 모든 schedule(daily 05:30·weather 4회·hospitals 월·cf-apps)이 여기서 돌고 결과(data/·logs/)를 여기에 커밋 | 돈다 | 아니오 |
| `main` | **앱(app/index.html `RAW = …/main/data/<구>/`)과 관리자가 읽는 가지**. 2026-11-03 00:08 수동 검문본 이후 갱신 없음 | 안 돈다(기본 가지가 아니라 schedule 무시) | **예** |
| `work` | 클로드 작업·시험 가지(022~028). `data/<구>/`가 **검문 전 상태(11파일, deals·jobs 포함)** 로 남아 있음 | 안 돈다 | 아니오 |

검증 방법: `git ls-remote`(세 가지 head), `app/index.html` 369~379행(RAW 주소), Actions 실행 기록(head_branch=daejeon-setup), `git ls-tree` 파일 수(main 5 · daejeon-setup 5 · work 11).

**결론**: 자동 수집 성공(기본 가지 커밋) ≠ 고객 화면 갱신. 감시(monitor.py)는 이제 `customer_view.fresh` 와 구별 `customer_stale` 장애로 이 둘을 구분해 알린다.

## 2. 위험 2가지(새로 확인)
1. **work → main 병합 시 data/ 역류**: work 의 `data/<구>/` 에 검문 전 파일(deals·jobs·sports·events·meals·elite·weather)이 남아 있어, 코드 반영을 위해 work 를 main 에 그대로 병합하면 **비공개 자료가 main 에 되살아날 수 있다**. → 코드 반영은 `data/`·`review/`·`ops/` 를 제외하고(`git checkout main -- data` 후 커밋 또는 경로 제한 PR), 자료 반영은 promote-main 으로만.
2. **기본 가지 ≠ 앱 가지** 상태가 계속되면 고객은 영구히 옛 자료를 본다(021·022·024·025 반복 지적).

## 4. 롤백 절차(준비됨, 미실행)
1. 자료 문제(잘못된 수집본 공개): Actions → **rollback-data** → 폴더(예 `yuseong`) · 기준 커밋(빈칸=직전 자료 커밋) · '승인' → main 의 `data/<구>/` 복원 + `ops/recovery_log.json` 기록 → cf-apps 는 앱만 올리므로 재배포 불필요(앱은 raw 를 바로 읽음).
2. 코드 문제(앱 화면 오류): main 에서 해당 커밋 `git revert` → cf-apps 수동 실행(앱 재배포). 관리자 역시 admin 워크플로.
3. 검문 규칙 문제: `tools/data_rules.json`·`change_rules.json` 을 직전 버전으로 되돌린 뒤 daily 수동 실행.
4. 확인 중(rv)·비공개 처리가 과했을 때: `approvals/reverify.json` 에 `result:"기각"` 기록 → 다음 수집에서 원래 값 복원(025).
